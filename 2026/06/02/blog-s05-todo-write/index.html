不给 Agent 加能力，只加结构 — s05 TodoWrite 学习笔记

一句话核心

“没有计划的 agent 走哪算哪”

s05 通过一个零执行能力、只有规划能力的 todo_write 工具，让 Agent 在动手之前先列步骤。它不读文件、不写文件、不跑命令——它唯一的作用是让 Agent 把自己的思路结构化地记下来。

这个设计思想贯穿了整个 Claude Code 的任务系统演进。

为什么需要这个

问题

给 Agent 一个多步骤任务：

“把所有 Python 文件改成 snake_case 命名，然后跑测试，修好失败。”

Agent 开始干活，改了 3 个文件，跑了个测试，发现 2 个失败，开始修。修着修着，它忘了最初是”改成 snake_case”——测试失败把注意力全吸走了。对话越长越严重，系统提示的影响力被稀释。一个 10 步重构，做完 1-3 步就开始即兴发挥，因为 4-10 步已经被挤出注意力了。

解决方案

在已有工具集（bash、read_file、write_file、edit_file、glob）的基础上，不改变任何现有逻辑，只新增一个工具：todo_write。

关键观察

  1. Nag 确实起作用了：两次 nag 都让 Agent 调了 todo_write，第一次列计划，第二次更新状态
  2. 但 Agent 仍然忘了更新状态：两步实际都完成了，但 TODO 状态一直显示 ▶ ◻，直到第二次 nag 才反应过来
  3. Agent 没有在第 1 轮就规划：即使 SYSTEM 提示写了”先规划再执行”，Agent 还是先读了文件再说

深入讨论：这个机制真的有用吗？

我在学习中的质疑

“提醒就是往对话里塞一条消息。如果上下文已经太长了，这条消息不也会被稀释吗？”

教学版 vs 真实 Claude Code

教学版 s05 真实 Claude Code
任务存放位置 对话历史的 messages 里 system prompt 顶部，每轮重新注入
Nag 方式 写死的 <reminder> 字符串 模型根据上下文动态生成提醒
上下文稀释 会，todo 被埋没在历史中 不太会，system 始终是最新的
对话太长 无处理 → Subagent 拆到独立对话
任务依赖 平铺列表 → Task System V2: blockedBy 依赖图

核心结论

todo_write 的真正价值不是”这个机制能完美解决问题”，而是展示一个设计思路：

不给 Agent 增加执行能力，只增加规划能力

一个不读文件、不写文件、不跑命令的工具，单纯通过”让 Agent 把自己的思路结构化地记下来”，就能显著改善多步骤任务的执行质量。

但正如测试结果所示——光靠 reminder 确实不够。它只是整个演进链路的第一环：

  • s05：内存列表 + nag reminder → 先学会列计划
  • s06 Subagent：把大任务拆成独立子任务，每个有干净上下文
  • s12 Task System V2：文件持久化 + blockedBy 依赖图 + 并发锁 + ownership
