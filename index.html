教学版 vs 真实 CC 的代码形状

关键差异

1. Schema 格式不同

教学版用 JSON Schema——API 原生支持，声明式。CC 内部用 Zod Schema——TypeScript 生态，支持复杂校验（正则、条件、变换）。但最终都是同一个目的：告诉模型参数长什么样。

2. 定义和实现在一起 vs 分开

教学版分开是为了教学清晰——一眼看到”加工具 = 2 步”。CC 把它们打包成一个 buildTool() 调用，更方便做统一验证和注入。

3. 教学版没有的机制

  • 并发安全：只读工具（read_file、glob、ls）可以并行执行，写工具（rm、write）串行。CC 根据 isConcurrencySafe 自动分区
  • 结果落盘：工具输出太大就写文件，模型只看到摘要 + 文件路径，避免上下文撑爆
  • 5 步验证管线：Zod 校验 → validateInput → PreToolUse hooks → 权限检查 → 执行

四、全过程复盘

执行路径一览

轮次 模型在想什么 调用了什么 结果
R1 先看文件行数 wc -l < code.py ❌ 文件不存在
R2 再试一种方式 cat code.py ❌ 还是不存在
R3 看看目录结构 ls -la ✅ 看到 29 个子目录
R4 全局搜索 find . -name 'code.py' ✅ 找到 20 个文件
R5 综合信息，直接回答 无 (end_turn) ✅ 循环结束

关键观察

1. 错误不是终点，而是信号

wc -l 返回错误后，模型没有崩溃——它把错误当成新信息，调整策略继续尝试。这是 Agent 模式与普通程序最大的区别：错误被喂回模型，让模型自己修正。

2. 思维链（Chain-of-Thought）自动涌现

第 2 轮开始出现了 thinking 块，模型在公开自己的推理过程：”看起来当前目录下没有 code.py 文件。让我先看看当前目录下有什么文件。” 这不是提示词要求的——是模型自然习得的推理能力。

3. 从直接到迂回，策略动态调整

模型的三次尝试策略越来越聪明：

  • R1：直接访问（wc -l）
  • R2：换个方式访问（cat）
  • R3：先了解环境（ls），再精确定位（find）

这种”失败 → 调整 → 再尝试”的迭代过程，正是人类工程师面对未知问题时的自然反应。

4. 循环次数=智能程度

这个例子跑了 4 轮。更复杂的任务可能跑几十轮甚至上百轮。每一轮都是：模型推理 → 行动 → 观察结果 → 再次推理。

五、总结

Agent Loop 的核心哲学：

人类给方向，AI 负责执行路径上的所有细节决策。

  • 你不需要告诉它”先用 ls，再用 find”——它自己会决定
  • 你不需要处理错误——它收到错误会自动调整策略
  • 你只需要一个循环、一个工具，就能让模型持续行动

这个最小的 20 行 while True，就是所有 AI 编码智能体的基础。后面的安全、权限、记忆、协作等机制，都是在这之上叠加的图层。但核心永不变：

循环不终结，智能不停止。

3. 真相大白：麒麟 ARM64 的 unpigz 是罪魁祸首

在反复查阅 Docker 源码和社区讨论后，怀疑是镜像层解压环节出了问题。Docker 在解压 gzip 压缩的层时，会优先调用 unpigz（并行解压工具）以提高性能。如果系统中存在 unpigz，Docker 会使用它；否则回退到标准的 gunzip。

在麒麟 ARM64 系统中，默认安装了 unpigz（由 pigz 包提供），但该 ARM64 版本的 unpigz 存在兼容性缺陷——解压后的 tar 流头部会损坏，导致 Docker 注册层失败。

验证方法：直接用 unpigz 解压一个正常的 .tar.gz 文件，再对比 gunzip 的结果，发现 unpigz 解压后的 tar 文件头部确实损坏。
