从 445 行到 224 行：CMOS Skill Phase-Gate 架构改造实战

基于旧版 cmos-mall-goods 改造为新版 cmos-biz-flow 的经验总结

一、背景与动机

在 CMOS 智能体开发中，我们发现随着业务复杂度增长，Skill 文档会逐渐膨胀为一个”巨无霸”——所有规则、流程、场景、示例全堆在一起，导致：

  1. 维护困难：规则重复出现在 3+ 处
  2. 执行飘忽：LLM 可能跳过关键步骤
  3. 新人劝退：读完整个文件才能动手

旧版 cmos-mall-goods 就是典型代表：445 行单体文件，包含提槽规则、价格映射表、模糊意图转换、多品类检测、40+ 分支决策树、场景流程、输出格式、Gotchas 等全部内容。

我们决定用它来”开刀”，验证 Phase-Gate 架构的可行性。

二、改造效果

指标 旧版 cmos-mall-goods 新版 cmos-biz-flow
SKILL.md 行数 445 行 224 行 (-50%)
顶层章节数 14 个 11 个
场景枚举 5 个模糊分类 12 个精确 scenario 值
是否有 Gate ❌ 无 ✅ 4 个 Phase Gate

三、Phase-Gate 执行引擎

这是本次改造的核心创新。把”读完全文再行动”变成”读一段、执行、验证、通过、下一步”：

每个 Phase 输出结构化 JSON

作用：

  • LLM 自我验证（各阶段输出可回溯）
  • 跨阶段数据传递（Phase 1 的 slots → Phase 2 的 category-groups → Phase 3 的工具调用）
  • 调试时可定位到具体 Phase 出错

四、设计模式总结

模式1：Quick Reference 速查表

文件最前面放一张意图→场景→工具链的映射表（13 行），LLM 可在不读任何执行流程的情况下完成场景路由。

模式2：单一来源 + 按需加载

  • SKILL.md = 架构 + 路由表 + 全局约束（~200行）
  • references/*.md = 完整执行细节 + 各自 Checklist（按需加载）

规则只在 SKILL.md 中定义一次，reference 文档通过 Gate 编号引用 SKILL.md 的约束。

模式3：Reference 文档 Checklist

每个 reference 文档以 Phase-Gate 检查清单结尾（markdown checkbox 格式），LLM 执行完该文档流程后逐项验证。

五、skill-creator 模式评审

使用 cmos-skill-creator 的设计模式标准进行评审：

维度 评估
设计模式 ✅ 符合 Pipeline（流水线）
核心痛点 ✅ 解决了”复杂任务跳步”问题
门控机制 ✅ 4 个 Phase + Gate 把关

潜在改进点

问题 严重程度 说明
Gate 3 描述过于笼统 中 “该场景所有适用门控均通过”未列出具体检查项
无跳步恢复机制 低 未说明重试上限

六、适用场景判断

七、后续 Skill 状态

Skill 行数 是否 Phase-Gate 建议
cmos-biz-flow 224 ✅ 是 参考标杆
cmos-plan 480 ❌ 否 最大单体，最需要改造
cmos-data-traffic 263 ❌ 否 可能在改造中
cmos-mall-phone 较小 ❌ 否 场景单一，优先级低

八、总结

Phase-Gate 架构的核心价值：

  1. 职责清晰：每个 Phase 专注一件事
  2. 可观测 DEBUG：每个 Phase 输出 JSON，出问题能快速定位
  3. 容错回退：Gate 不通过则重做
  4. 可扩展：新增场景/工具只需修改对应 Phase

它不是银弹——简单场景（≤3 个场景）反而增加不必要的复杂度。但对于 cmos-biz-flow 这类场景多、工具多、有依赖链的复杂业务，效果显著。

本文档基于 cmos-skill-creator 规范评审，相关代码已沉淀到 CMOS Skill 库。

麒麟 ARM64 系统 Docker 踩坑记：从代理配置到"invalid tar header"的终极解决方案

2. 噩梦开始：拉取 arm64v8/ubuntu:22.04 时反复出现 invalid tar header

为了获得一个可交互的 ARM64 环境，我选择拉取官方 Ubuntu 22.04 ARM64 镜像：

拉取进度到解压层时，突然报错：

多次重试、换用其他镜像（如 arm64v8/alpine:3.18）均在同一阶段失败。错误信息指向 tar 头部损坏，但镜像源本身是可靠的（在其他架构上正常）。

2.1 常规排查手段均无效

  • 清理 Docker 存储：docker system prune -a，删除 /var/lib/docker 后重启。
  • 切换存储驱动：从 overlay2 改为 aufs、devicemapper 测试。
  • 迁移数据目录：换到另一块磁盘。
  • 重装 Docker：卸载后重新安装最新版。

所有方法都无法解决问题，错误依旧。

3. 真相大白：麒麟 ARM64 的 unpigz 是罪魁祸首

在反复查阅 Docker 源码和社区讨论后，怀疑是镜像层解压环节出了问题。Docker 在解压 gzip 压缩的层时，会优先调用 unpigz（并行解压工具）以提高性能。如果系统中存在 unpigz，Docker 会使用它；否则回退到标准的 gunzip。

在麒麟 ARM64 系统中，默认安装了 unpigz（由 pigz 包提供），但该 ARM64 版本的 unpigz 存在兼容性缺陷——解压后的 tar 流头部会损坏，导致 Docker 注册层失败。

验证方法：直接用 unpigz 解压一个正常的 .tar.gz 文件，再对比 gunzip 的结果，发现 unpigz 解压后的 tar 文件头部确实损坏。

6. 总结

  • 代理问题：Docker 拉取镜像时如需代理，需设置 http_proxy/https_proxy 环境变量（或写入 Docker 服务配置）。
  • invalid tar header 错误：在麒麟 ARM64 系统上很可能是由 unpigz 的兼容性问题引起。重命名 unpigz 让 Docker 回退到 gunzip 即可完美解决。
  • 副作用：移走 unpigz 不会影响系统其他功能，解压速度会稍有下降，但稳定性优先。
